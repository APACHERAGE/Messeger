## 1. Краткое резюме

Приложение в целом работает корректно: авторизация, профиль, стена и лента, каналы, обсуждения, чаты, почта, контакты, друзья, подписки, блокировки и жалобы — все основные сценарии проходят, включая проверки прав доступа. Разграничение доступа (403/404 вместо утечки данных), CSRF, ротация сессии, одноразовые токены и валидация медиа реализованы аккуратно.

Найдено **2 заметных дефекта** и **ряд мелких**:

| № | Серьёзность | Проблема |
|---|---|---|
| B1 | **Высокая (UX)** | При каждой загрузке приложения появляется ложная ошибка «Failed to load messages.» и уходит 404-запрос на несуществующий чат `my-chat`. Тост не исчезает сам — его нужно закрывать вручную. |
| B2 | **Средняя** | На мобильном (390 px) горизонтальный скролл: шапка растягивает страницу до 419 px на всех экранах. |

| B4 | Низкая/средняя | `avatarDataUrl` принимает `data:image/svg+xml` без проверки типа (потенциальный stored XSS при смене способа рендера). |

| B6 | Низкая | На мобильном нет постоянной навигации: CSS `.hub-mobile-nav` есть, компонента нет; доступ к разделам — только через палитру команд. |
| B7 | Низкая | `PUT /api/profile` без семантики PATCH: незаполненные поля затираются. |

## 2. Окружение и методика

### 2.1 Что было запущено

| Инстанс | Порт | Назначение | Как запущен |
|---|---|---|---|
| «Живой» | 8080 | Текущий рабочий сайт, отдаёт собранный SPA | `java -jar target/messenger-api-0.1.0.jar --app.mail.mode=console --app.auth.public-url=http://localhost:5173` (pid 108788) |
| QA-инстанс | 8081 | Полный прогон с аутентификацией | тот же jar, отдельная H2-БД `/tmp/opencode/qa/nightfall-qa`, `--app.auth.public-url=http://127.0.0.1:8081` (pid 127285) |

Почему два инстанса: письма (подтверждение e-mail, сброс пароля) в режиме `console` печатаются в stdout процесса. У живого инстанса stdout — это pty `/dev/pts/6`, который извне не читается, поэтому подтвердить тестовый аккаунт на 8080 невозможно. Живой инстанс тестировался только без аутентификации, чтобы не засорять реальные данные и не тратить его rate-limit. Полный функциональный прогон шёл на одноразовой копии с той же сборкой jar.

## 5. Дефекты

### B1. Ложная ошибка «Failed to load messages.» при каждой загрузке (высокая, UX)

**Где:** `src/App.tsx:62` (`useState('my-chat')`), эффект загрузки сообщений `src/App.tsx:223–238`, замена id в `src/App.tsx:183`.

**Шаги:**
1. Войти в приложение (десктоп или мобильный).
2. Подождать 1–2 секунды.

**Факт:** внизу появляется тост «Failed to load messages.» (`role="status"`), в Network — `GET /api/chats/my-chat/messages?limit=100` → 404. Тост не исчезает сам: он живёт до нажатия «Dismiss notification» или до замены другим уведомлением. На мобильном при переходе между разделами 404 повторяется (наблюдалось 7 раз за прогон).

**Ожидание:** никаких ошибок при обычной загрузке.

**Причина:** начальное состояние `selectedId = 'my-chat'` — это демо-заглушка, которой на сервере не существует. Эффект загрузки сообщений срабатывает сразу после перехода `authMode` в `online`, то есть **до** того, как `listChats()` + `getOrCreateSelfChat()` в эффекте на строке 174–189 заменят id на реальный `selfChat.id` (строка 183). 404 попадает в `.catch()` и вызывает `setNotice('Failed to load messages.')`.

**Почему это важно:** пользователь видит ошибку при каждом входе и вынужден закрывать её вручную; это подрывает доверие к приложению и маскирует настоящие ошибки загрузки сообщений.

**Как исправить (минимально):**
- `const [selectedId, setSelectedId] = useState<string | null>(null)` — и в эффекте загрузки уже есть проверка `if (!selectedId) { setLoadingMessages(false); return }`, так что 404 просто не будет.
- Либо не показывать ошибку, пока `loadingChats` не завершился, и не считать 404 для id, которого нет в `chats`, ошибкой.

**Проверка:** после правки при загрузке не должно быть запроса на `my-chat` и тоста.

### B2. Горизонтальный скролл на мобильном: 390 → 419 px (средняя)

**Где:** `src/styles.css:40–45` (`.app-shell`, `.masthead`), медиазапрос `@media (max-width: 760px)` — `src/styles.css:295–302`.

**Шаги:**
1. Открыть приложение при ширине окна 390 px.
2. Проверить `document.documentElement.scrollWidth`.

**Факт:** `scrollWidth = 419`, `clientWidth = 390` на всех экранах (`/`, `/threads`, `/channels`, `/mail`, `/contacts`, `/messages`, `/settings`). Виновник — шапка: `.masthead` шириной 419 px, внутри `.wordmark` (173 px) + `.masthead-actions` (212 px) + отступы 26 px. Контент страницы (посты) из-за этого тоже выходит за экран.

**Причина:** `.app-shell` — грид с единственной неявной колонкой, которая растягивается по max-content шапки (в замере `grid-template-columns: 418.703px`). У `.wordmark` нет `min-width: 0`, поэтому flex-элемент не сжимается, и вся сетка становится шире вьюпорта.

**Подтверждённое исправление** (проверено инъекцией CSS в браузере: `scrollWidth` становится 390):

```css
@media (max-width: 760px) {
  .app-shell { grid-template-columns: minmax(0, 1fr); }
  .masthead { min-width: 0; }
  .wordmark { min-width: 0; flex: 0 1 auto; overflow: hidden; }
  .masthead-actions { flex: 0 0 auto; }
}
```

Дополнительно стоит на узких экранах скрывать подпись `DEVOPS · CODE · COMMUNITY` в `.wordmark`, чтобы логотип не обрезался.

### B3. Сообщения валидации и пустой 413 (средняя)

| Случай | Ответ | Проблема |
|---|---|---|
| Имя из 49 символов (лимит 48) | `{"message":"Enter your first name."}` | Сообщение не соответствует причине — пользователь думает, что поле пустое |
| Аватар > 1 МБ | `{"message":"Check the submitted fields."}` | Нет указания, какое поле и какой лимит |
| 4 × 8 МБ вложений | `413`, **тело пустое** | Клиент не может показать осмысленную ошибку |

**Где:** `backend/.../ApiErrorHandler.java` (маппинг сообщений), обработка `MaxUploadSizeExceededException`.

**Как исправить:** для `firstName`/`lastName` различать «пусто» и «слишком длинно» («First name must be 48 characters or fewer.»); для `avatarDataUrl` добавить отдельное сообщение («Avatar must be 1 MB or smaller.»); добавить обработчик `MaxUploadSizeExceededException` с JSON-телом `{"message":"Attachments must total 30 MB or less."}`.

### B4. `avatarDataUrl` принимает SVG без проверки типа (низкая/средняя, потенциальный stored XSS)

**Шаги:** `PUT /api/profile` с `avatarDataUrl = "data:image/svg+xml;base64,<svg><script>alert(1)</script></svg>"`.

**Факт:** `200`, значение сохраняется и возвращается как есть. Лимит 1 МБ работает, тип — нет.

**Почему это пока не эксплуатируется:** аватар рендерится как `<img src={avatarDataUrl}>`, а SVG внутри `<img>` не исполняет скрипты. Но это единственное место, где данные URL не проходят через `DataUrlAttachment`, который для вложений явно запрещает SVG и HTML. Любой будущий рендер через `object`/`iframe`/CSS `background`/`dangerouslySetInnerHTML` превратит это в stored XSS.

**Как исправить:** прогонять `avatarDataUrl` через `DataUrlAttachment` (разрешены только png/jpeg/gif/webp + проверка сигнатуры), как это уже сделано для фото комментариев и вложений чата.

### B5. Отсутствуют современные заголовки безопасности (низкая)

На `/` присутствуют `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`. Отсутствуют `Content-Security-Policy`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security` (последний актуален только для HTTPS).

**Рекомендация:** добавить как минимум

```
Content-Security-Policy: default-src 'self'; img-src 'self' data: blob:; media-src 'self' blob:; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

CSP придётся согласовать с Vite-сборкой (инлайновые стили/модули), поэтому начинать лучше с `Content-Security-Policy-Report-Only`.

### B7. `PUT /api/profile` затирает незаполненные поля (низкая, API-дизайн)

**Шаги:** отправить `PUT /api/profile` с телом `{"username":"qa_beta"}`.

**Факт:** `200`, при этом `displayName`, `headline`, все флаги и `preferences` сбрасываются в дефолты/пустые значения.

**Причина:** DTO — плоский набор полей без различения «не передано» и «пусто»; метод полагается на то, что клиент всегда присылает полный объект.

**Как исправить:** либо перейти на `PATCH` с `Optional`/`JsonNullable`-семантикой, либо требовать полный объект и отвечать 400 при отсутствии обязательных полей. Сейчас это ловушка для любого нового клиента/интеграции.

---

### B8. HTML в тексте поста сохраняется без серверной обработки (инфо)

`POST /api/hub/posts` с телом `<img src=x onerror=alert(1)> xss probe` → `201`, текст хранится дословно. В UI React экранирует вывод, поэтому выполнения скрипта нет. Это допустимо, но стоит зафиксировать в документации: безопасность здесь целиком на клиенте.

- **Медиа:** поддельный PNG (неверная сигнатура) → 400; фото 6 МБ → 400; вложение чата `text/html` → 400; имя файла с `../` → 400.
- **Каналы:** `javascript:`-ссылка → 400; комментарии закрыты на уровне канала и отдельного поста; закрепление поста; передача владения только подписчику; удаление только с точным названием.
- **Обсуждения:** ответ на комментарий из другой темы → 404; принятие ответа из другой темы → 400; снятие «решено» очищает принятый ответ.
- **Почта:** отправка себе/внешнему/несуществующему ящику → 400; пустая тема → 400; тело 20 001 символ → 400; `limit=999` и `limit=-5` корректно клампятся.
- **Ошибки:** кривой JSON → 400, неверный метод → 405, повторная заявка в друзья → 409, занятый username → 409.
- **Сборка и тесты:** `npm test` — api, account, posts, social, appearance, channels, navigation — все прошли; `npm run build` — успешно.

## 7. Ограничения тестирования

1. **Живой инстанс (8080) проверен только без аутентификации.** Причина: ссылки подтверждения и сброса печатаются в stdout процесса, а он направлен в pty `/dev/pts/6`, недоступный для чтения. Поэтому тестовый аккаунт на живом сайте **не создан**. Функциональность проверялась на идентичной сборке (тот же jar) на 8081.
2. **Нет визуальной экспертизы дизайна.** Скриншоты снимались для проверки рендеринга и переполнения; pixel-perfect, типографика и доступность (контраст, фокус, скринридер) отдельно не оценивались.
3. **Не проверялись:** реальная отправка e-mail через SMTP (только console-режим), восстановление после падения БД, конкурентные гонки (одновременные заявки/реакции), длительная нагрузка, реальные мобильные браузеры (Safari/iOS), PWA/офлайн.
4. **Rate-limit на QA-инстансе исчерпан** к концу прогона (30 логинов / 15 минут на IP), поэтому финальные UI-проверки выполнялись с переиспользованием существующей сессии через cookie, без нового логина.
5. **`npm run build` перезаписал `dist/`** в рабочей копии. Хеш основного бандла совпал с тем, что отдаёт живой сервер (`index-De9u3tyL.js`), поведение 8080 не изменилось.
